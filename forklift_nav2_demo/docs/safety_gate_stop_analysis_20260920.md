# 920 Safety Gate 与停车异常分析

本轮只做离线诊断，没有修改运行代码、碰撞阈值或车体尺寸。

数据：`ros2bag/920/planning_debug_20260920_{155658,160928,161049,161217,161623,161852,162033}`。
日志：`ros2bag/920/920log/920/log`，并使用 bag 内 `/rosout` 对齐事件。
SQLite 只读解析；对比原始命令、门控命令、车辆反馈、scan、目标、路径、任务状态及定位。
下面秒数均相对各自 bag 开始时间，不是日志中的绝对时间。

## 1. 原始命令到门控输出存在明显滞后

| 包 | `/control_cmd_raw` 首次停止 | `/control_cmd` 对应停止 | 接收时间差 |
| --- | --- | --- | --- |
| 160928 | 61.653 s | 62.110 s | 0.457 s |
| 161049 | 52.017 s | 52.500 s | 0.483 s |
| 162033 | 98.076 s | 98.587 s | 0.511 s |

非零命令按速度、转角、方向、制动字段匹配后，各包源命令时间到 gate 输出时间的 P95 约为 0.48–0.52 秒。原始命令和对应 gate 停止消息各自的 header 到录包时间通常只有几毫秒，不能只用“录包写盘慢”解释上述停止边沿差异。

高度怀疑 Safety Gate 的订阅积压和同步碰撞计算共同导致：

- `safety_command_gate.py::_on_timer()` 同步执行 scan 与 costmap 扫掠，再发布命令。
- 原始命令订阅为 depth=10，默认单线程 executor；20 Hz 下十帧就是约 0.5 秒。
- `_on_raw_command()` 按回调执行时间更新新鲜度，不检查原命令 header；排队的旧命令会被当成刚收到。
- `_latest_safe_command()` 将输出 header 改成当前时间，因此下游单看输出 header 看不到上游命令积压。

队列积压是代码与数据支持的解释，不是已经测得的独立 CPU/DDS 根因。需要补充 callback 开始时间、输入 stamp、每层检查耗时和发布时刻区分。

在约 1 m/s 时，0.5 秒就是额外约 0.5 m。终点附近零速发出后反馈速度仍约 0.6–0.9 m/s，最终偏离目标约 0.38–0.53 m，与停止迟到和制动余程一致。

另外，Controller 对 pending pivot 使用带反应时间的 `stoppingSpeedLimit()`，普通终点主要依赖轨迹速度反向传播和到点停止；`previewSpeedLimit()` 跳过零速度点。终点控制还需要独立复核，不应仅靠加大到点容差掩盖越界。

图：[终点命令、反馈与距离](gate_terminal_stops_20260920.png)。图中对齐为录包接收时间和最新消息保持，不是 CAN 链路延迟测量。

## 2. Pivot 被按照过长的后续旋转扫掠检查

`scan_sweep_collision()` 使用 `horizon = stopping_distance / command_speed`，而停止距离含固定 0.5 m 余量。

以 155658 约 26.12 秒为例：

- 命令速度 0.05 m/s，pivot 半径 0.6 m。
- `d_stop = 0.05 * 0.9 + 0.05^2 / 3 + 0.5 = 0.546 m`。
- 预测约 10.9 秒，离散扫掠约 52.5 度。
- 当前实际剩余目标角约 20.3 度；按该帧 scan 复算首次碰撞在约 47.7 度。

这证明所记录的拒绝位置超出了请求剩余旋转，不证明实车能够无制动余程地在目标角停车。不能简单把预测裁成剩余角就宣布安全。

`stop_command()` 还把 steering 清零。记录里随后出现舵角从约 1.57 降到 1.3，Controller 重新等待满舵，然后再次触发碰撞停车，形成重复循环。

图：[剩余旋转与碰撞扫掠](gate_pivot_sweep_20260920.png)。黑色当前外廓，绿色剩余目标姿态，红色首次碰撞预测姿态；碰撞计算包含 0.05 m padding。

建议单独建立 pivot 角制动模型，使用真实/保守角速度、反应时间、角减速度和外廓余量。普通障碍暂停时评估保持当前安全舵角，不把急停、故障和普通暂停混为同一种转向动作。保留完整旋转碰撞检查。

## 3. 161623 的最后一次不是单纯误拦

114.394 秒附近 Controller 日志：

```text
max_curvature=22.469 allowed=1.667
reverse_points=8 pivot_points=2 direction_changes=11
```

120–140 秒记录同时存在：

```text
controller_debug.segment_state: reverse
control_cmd_raw.velocity_mps: 0.09
control_cmd_raw.forward: true
control_cmd_raw.reverse: false
safety_gate/status: scan footprint sweep collision
```

`ForkliftMpcController::computeVelocityCommands()` 在 reverse 模式仍枚举正向候选，只额外添加负向候选；`scoreCandidate()` 缺少当前 motion block 的方向硬约束。因此存在选中正向命令的代码路径。

Safety Gate 根据实际 raw command 而非调试标签检查前进碰撞，这是应保留的保护。需要先修复运动段方向约束、cusp/轨迹整理及超限曲率处理，不能用降低 scan 灵敏度解决。

## 4. 161852 新目标可能继承旧路径

时间线：

1. 45.309 秒开始旧 anchor，目标约 `(-15.241, 35.949)`。
2. 45.34 秒收到新的导航目标，约 `(-15.368, 30.659)`。
3. 45.371 秒 BT 接受 preemption。
4. 45.413 秒发布的路径仍结束于旧 anchor，约 `(-15.22, 35.96)`。
5. 59.547 秒 Nav2 报成功，Task Manager 随后也报告新任务成功；并未到新目标。

代码中 `Nav2Navigator.cancel_goal()` 发异步取消但不等待旧 action 终态，新目标随即发送。当前 plan-once XML 使用 Sequence，规划完成后进入 FollowPath，不会因为 goal blackboard 更新就必然重新规划。旧回调 token 防护不能替代服务端行为树的目标/路径一致性。

应串行完成取消与新目标接管，并在执行及最终成功时检查任务 goal、路径终点和实际到达位置的一致性。不能仅靠固定 sleep 或重启节点。

## 修复与验证顺序

1. 优先修 gate 输入新鲜度、命令队列及检查耗时；原始停止优先处理，过期检查结果不得覆盖更新的停止命令。失去新鲜数据应停车，不能复用旧的安全判定继续走。
2. 独立处理 pivot 角制动扫掠和停止后的舵角状态；用 155658/161217 静态帧复算，同时验证真实目标范围内新增障碍仍能停车。
3. 修普通终点提前制动和停车确认；复现 160928/161049/162033，既测 raw 到 gated 延迟，也测 gated 到车辆停稳余程。
4. 修复 reverse motion block 的方向一致性及异常轨迹，复现 161623；倒车期间不得选择正向非零命令。
5. 修取消/抢占与路径一致性，复现 161852 的约 50 ms 内重发目标，不得在旧 anchor 误报新目标成功。

本轮完成了日志核对、只读 bag 解析、scan 几何复算和绘图；没有做修复后的构建或实车验证。不能据此关闭安全门、缩小真实车体或直接提高车速。
